## Theme: Remote areas and review

Documents that may not live in Git, and a review loop through SharePoint, with Git as the truth. A project declares named areas in `stanza.yaml`, each with a SharePoint URL and a use: `reference` (files that documents point to, such as evidence), `exchange` (a DOCX goes out for review and the comments come back) or `publish` (published output). Nothing in Stanza knows what the files are for. The only transport is a folder: an area is mounted at `remote/<name>/`, which is never tracked by Git, and the folder is the one that the OneDrive client has synced for that URL. Command-line tools (`m365`, rclone) were ruled out, since they need an app registration or admin approval, and Stanza holds no credentials. CI only publishes and never pulls. Reviews are ordinary unlisted documents (ADR 0072) with one heading per comment, linked to the block by `#id` (ADR 0068), and the status is plain text until forms exist (items 99 to 103). No new document type.

The review loop itself is done (items 138 to 141, 203, 211, 212 and 214), with the checks left from its spike in item 233: it works with file paths first, and the areas below then make a synced SharePoint folder the transport. Items 38 and 39 (importing and showing Word comments) were merged into items 140 and 141.

## Theme: Content inclusion and source excerpts

Compose documents from single-sourced fragments in other Stanza documents or marked source-code comments. The defining text stays in one place; each consuming document stores an inclusion reference, not a copied expansion. Text can stay next to the code it describes, while documents supply the order, headings and narrative for different audiences. Editor and export resolve the current local sources; Git preserves reproducible revisions. This is ID-based transclusion, not a general templating language.

152. [L] - ID-based content inclusion, design and ADR: include an identified fragment from another Stanza document or a marked source-code comment, read-only initially. Consider `![label](relative-file#id)` for inclusion, distinct from `[label](target)` navigation, instead of assuming a `stanza-include` block; settle the dialect, disambiguation from real images and ordinary Markdown/GitHub behavior before implementation. This is a proposed Stanza extension, not existing Markdown transclusion. IDs are authoritative and filenames are checked hints. Define explicit fragment boundaries, including heading-only versus whole-section inclusion; no arbitrary line ranges. Short text may be included inline, while lists, tables and sections require block placement; incompatible placement is a diagnostic. Keep origin visible and provide navigation to the definition; links within included text retain their source context. Settle metadata resolution context with items 146 and 200, nesting and separation of source identity from rendered occurrence identity for repeated inclusions, DOCX bookmarks, reference destinations and review anchors; never duplicate or reassign source IDs to represent appearances. Missing or duplicate targets, inclusion cycles and paths outside the project/repository are diagnostics, never stale cached text. For source comments, retain the marker approach (`// stanza: #<id>`), restricted Markdown fragments (paragraphs, lists, marks, code), project-declared scan globs, a comment-style table per extension and line comments first; inspect marker lines without parsing or executing the language, and assign IDs only on markers. Resolve against the local working tree and index incoming inclusions for Find references (item 126). Discuss with the product owner before any code. Extends the colocation discussion of 2026-11-13 with document composition requested by the product owner.
153. [L] - Included content, explicit editing and write-back: a later, deliberate shared-source edit mode for included Stanza fragments and source comments, separate from the initial read-only inclusion. Show the origin and make clear that an edit affects every consuming document; save only to the defining source, never silently detach or copy the fragment. Preserve source IDs and unrelated content. For comments, keep indentation and comment style, refuse text that would break the comment (for example `*/` in a block comment), and read the file again to check the result. A change of the defining file from outside is handled as in ADR 0062. Line comments first for source-code write-back. Depends on item 152.
154. [M] - Code regions in documents: embed a region of a source file, identified by a stable ID with explicit boundary markers, as a code block, read-only, with its language and a "go to source" link, so that an example is real code that is compiled and tested. The same inclusion mechanism as item 152; a missing region is a diagnostic. Depends on item 152; highlighting by item 167.
155. [S] - Open the source beside the editor: a command and an origin link from an included Stanza fragment, source comment or code region that open the defining document at its block or the source file at its marker, beside the consuming editor. Build on ID navigation (ADR 0077), ADR 0063 and item 174; no copied editing surface. Depends on item 152.
156. [M] - Inclusion peek panel: show a read-only preview of the defining Stanza fragment or the code/comment context around its marker without leaving the consuming editor, with origin and navigation; syntax highlighting for source code (item 167). Coordinate with link-target peeking in item 195 instead of creating unrelated preview mechanisms. Depends on item 155.
198. [M] - Shared single-sourced values: extend items 199 and 200 to values defined once for multiple documents, such as a product name, limit, version or service level, in project metadata or typed records (item 135). Resolve the value in editor, rendering and export without storing a copied expansion; unknown or missing values are diagnostics. Coordinate source identity, notation and compatibility with the broader inclusion design (item 152), including whether `![label](target)` applies and whether existing metadata tokens should migrate. Depends on items 200 and 152; typed-record sources also depend on item 135.
