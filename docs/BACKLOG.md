## Theme: Remote areas and review

Documents that may not live in Git, and a review loop through SharePoint, with Git as the truth. A project declares named areas in `phrase.yaml`, each with a SharePoint URL and a use: `reference` (files that documents point to, such as evidence), `exchange` (a DOCX goes out for review and the comments come back) or `publish` (published output). Nothing in Phrase knows what the files are for. The only transport is a folder: an area is mounted at `remote/<name>/`, which is never tracked by Git, and the folder is the one that the OneDrive client has synced for that URL. Command-line tools (`m365`, rclone) were ruled out, since they need an app registration or admin approval, and Phrase holds no credentials. CI only publishes and never pulls. Reviews are ordinary unlisted documents (ADR 0072) with one heading per comment, linked to the block by `#id` (ADR 0068), and the status is plain text until forms exist (items 99 to 103). No new document type.

## Theme: Source includes

Text next to the code it describes, included in documents by ID. The atoms (short statements that must stay true) stay in source files, and the order, headings and narrative stay in the Phrase document. The same atom can appear in more than one document.

152. [L] - Source includes, design and ADR: a comment block in a source file is marked with an ID in the comment syntax of the language (`// phrase: #<id>`), and its text is a restricted Markdown fragment (paragraphs, lists, marks, code). A document includes it by ID, not by path or line, as a `phrase-include` block (to settle: the form in the file, and how GitHub shows it). `phrase.yaml` lists the globs of the files to scan; only marker lines are looked for and the language is never parsed; a table of comment styles per file extension, line comments first. `format --assign-ids` writes IDs only on marker lines. Diagnostics: a missing target, an ID that occurs twice in the files, a path outside the project or repository root. The build resolves the includes against the working tree. Find references (item 126) works in both directions. Discuss with the product owner before any code. Added after the colocation discussion of 2026-11-13.
153. [L] - Source includes, editing and write-back: an included comment is editable in place in the editor, marked with its origin, and is saved back into the marked comment of the source file. The write changes only the comment: it keeps the indentation and the comment style, refuses text that would break the comment (for example `*/` in a block comment), and reads the file again to check the result. A change of the source file from outside is handled as in ADR 0062. Line comments first. Depends on item 152.
154. [M] - Code regions in documents: embed a region of a source file between named markers as a code block, read-only, with its language and a "go to source" link, so that an example is real code that is compiled and tested. The same mechanism as item 152, with region markers; a missing region is a diagnostic. Depends on item 152; highlighting by item 76.
